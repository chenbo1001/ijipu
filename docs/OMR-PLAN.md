# 方案：简谱图片 → `.jps` 脚本（OMR → iJipu 源码）

> 状态：**待用户裁决**（2026-10-11）。本文只做设计，不含实现。
> 目标一句话：**给一张简谱图片，输出符合 iJipu `.jps` 语法规则的源码**（可被引擎解析、可渲染、可试听），
> 并且**对不确定处不猜** —— 而是给出"待确认清单"，用户在界面上一次点完。
> 语法唯一口径：`docs/SYNTAX.md`（AGENTS §五·1）；贴图能力落点见 §6。

---

## 〇、先说三个"本项目的独特优势"（决定了这个方案能做得比别人稳）

1. **引擎可渲染 ⇒ 可以自动对答案** ✓
   我们能把生成的 `.jps` **渲染回 SVG**，与**原图叠图比对**（每个音符的墨迹矩形 vs 原图检测框 ✓）。
   这是 OMR 里最贵的"自动验收"环节，我们**天生就有** —— 别的项目要靠人工抽查 ✓。
2. **标签天然是文本** ✓
   训练/评测不需要画框：`samples/*.jps` **反向渲染成图片**即可得到"图 ↔ 源码"配对 ✓
   ⇒ **零人工标注**就能起步（P0 完全免费 ✓）。
3. **已有点选联动基建** ✓
   引擎的 `cursorMap` / `data-notepos` 让"**点原图某处 → 跳到源码对应 token**"和反向跳转都能做，
   ⇒ 人工修正界面不必从零造 ✓。

## 一、目标与非目标

**目标（按优先级）**
1. **单声部数字简谱**（`Q:` 行 + `C:` 歌词行 + 调号/拍号/速度）⇒ 生成可解析、可渲染的 `.jps`；
2. 逐元素**置信度**与**待确认清单**（低置信不硬猜 ✓）；
3. **叠图复核**：原图与"生成源码渲染结果"叠加对比，一眼看出哪里错 ✓；
4. 交互式修正：点原图/点渲染图 ⇒ 定位到源码 token 改 ✓；
5. 落点：**应用（桌面+手机）、Obsidian 插件、CLI** 三处都能用同一套能力（§6）。

**非目标（首版明确不做）**
- 手写谱、五线谱、模糊翻拍、多重曝光等极端输入；
- 多声部/临时段（`{bz}`/`{dsb}`/`{tp}`）/复杂装饰音的全自动识别（**先识别出结构、标记"待确认"** ✓）；
- 不追求"一次全对"：**追求"错得可见、改得快"** ✓（这是产品可用性的关键 ✓）。

## 二、总体架构（六层，逐层可独立验证）

```
图片
 └─① 预处理        灰度 / 去噪 / 二值化 / 倾斜纠偏 / 透视校正 / 分页
     └─② 版面分析   行带切分（水平投影）：标题区 / 调号拍号区 / 谱行 / 歌词行 / 页脚
         └─③ 符号检测  数字 0–7、八度点、减时线、增时线、附点、小节线、连音线/括号、
                      调号（1=C 等）、拍号（4/4）、速度（♩=60）、歌词汉字与标点、修饰符
             └─④ 语义装配  几何 → 音乐语义：
                          音高 = 数字 + 八度点（上/下）
                          时值 = 1 − 减时线数量 + 增时线 + 附点
                          分组 = 小节线位置（小节内时值校验交给引擎 ✓）
                 └─⑤ 语法生成  → `.jps` 文本（**只允许 `docs/SYNTAX.md` 里的合法 token** ✓）
                     └─⑥ 自检闭环 引擎 `parseJps` 校验 → 失败则**带错误信息回修**（见 §4.2）
                          └─⑦ 复核 UI  原图 vs 渲染图叠图 + 待确认清单（见 §4.3）
```

**每层的验收方式**（都可自动化 ✓）：
| 层 | 判据 |
|---|---|
| ① | 二值化后谱行区域"墨迹占比"稳定；纠偏后基线角度 < 0.5° |
| ② | 行带数量与真值一致（反渲染图上是已知的 ✓） |
| ③ | 符号级 **F1**（检测框 IoU ≥ 0.6 记命中） |
| ④⑤ | **文本级编辑距离**（生成 `.jps` vs 真值 `.jps`） |
| ⑥ | `parseJps` 错误数 = 0（或错误都在"待确认"里 ✓） |
| ⑦ | 叠图：每个音符墨迹矩形与原图检测框 **IoU 均值** |

## 三、技术路线三选一（请你裁决）

| 路线 | 做法 | 优点 | 代价/风险 | 适用 |
|---|---|---|---|---|
| **A 纯本地 CV** | OpenCV（WASM/Rust）：投影切行 + 连通域 + 模板/特征分类 | 零外网、零费用、可离线、可手机 | 准确率天花板低（倾斜/粘连/手写就崩）；**规则维护成本高** | 干净扫描件、批量预处理 |
| **B 本地深度模型** | 检测（YOLO 系）+ 序列识别（CRNN/TrOCR）；导出 ONNX 供 Tauri/移动端 | 离线、隐私好、可控 | **需要标注数据与训练工程**（本项目当前无此基建）；模型体积/性能在手机端要调 | 长期正解、隐私敏感场景 |
| **C 多模态大模型 API** | 把图给 VLM（含 `docs/SYNTAX.md` 摘录 + few-shot），要求**结构化输出** | 起步最快、泛化好、无需标注 | 外网/费用、**幻觉**（会编音符）、隐私（谱面外传） | **P0–P2 主路线**（配合 §4.2 自检闭环） |

**推荐组合（本方案主张）**：
> **C 起步（快速可用）+ ⑥引擎自检闭环（压幻觉）+ ⑦人工确认界面（兜底）**，
> 同时用**反渲染生成的合成数据**训练 **B**（离线/隐私增强），
> **A** 只用于预处理（切行/纠偏）——三层各司其职，不互相替代。

## 四、关键设计（这四条决定"好不好用"）

### 4.1 让模型**只能**说合法语法（受约束解码）
- 把 `docs/SYNTAX.md` 编译成**受约束输出**：
  · 提示词里给出**语法摘要 + 3–5 个 few-shot**（同风格：单声部 + 歌词 + 调号拍号）；
  · 要求输出**逐行 JSON**（不要自由文本 ✗）：
    ```json
    { "header": { "title": "...", "key": "1=C", "meter": "4/4", "tempo": 60 },
      "lines": [ { "type": "music", "tokens": [ { "kind": "note", "digit": 6, "octave": -1,
                     "underline": 1, "dotted": false, "conf": 0.93, "bbox": [x,y,w,h] } ],
                   "lyrics": ["让","我","再","看","你","一","遍"] } ] }
    ```
  · **bbox 必须给**（没有框就没法叠图复核 ✗ ⇒ 这一步是硬要求 ✓）；
- 生成器再把 JSON → `.jps` 文本（**这一步是我们的代码**，不交给模型 ⇒ 语法 100% 合法 ✓）。

### 4.2 引擎自检闭环（压幻觉的核心手段）
```
模型输出 JSON → 生成 .jps → parseJps() 自检
   ├─ 无错：进入 ⑦ 复核
   └─ 有错：把【错误清单 + 出错行上下文】回喂模型，要求**只修这几处**（最多 2 轮）
            仍不过 ⇒ 该行进"待确认清单"，交人工（绝不静默产出坏谱 ✗）
```
另外两条硬校验（都在引擎侧，纯函数 ✓）：
- **小节时值校验**（引擎已有：`第 N 小节共…`）⇒ 小节内拍数不合法即视为识别错误 ✓；
- **渲染成功**（`renderScoreToSvg` 不抛且产出非空）✓。

### 4.3 复核界面（原图 ↔ 谱面 ↔ 源码 三向联动）
- 布局：**左=原图（可缩放/框选）、中=渲染结果、下=`.jps` 源码**；
- 每个识别元素**带 id**（`LayoutId` ✓ 引擎已有）：点原图框 → 高亮渲染对应音符 + 源码对应 token；反向亦然 ✓；
- **待确认清单**（右侧列表）：低置信元素、自检失败行、时值不符小节 ⇒ 点一条跳一处，键盘上一个/下一个 ✓；
- **批量确认**：同类错误（如"全部低八度点漏识别"）可一键应用 ✓。

### 4.4 置信度与"不猜"原则
- 单一元素置信度 `< 阈值`（建议 0.85）⇒ **标记待确认**，不塞进正文；
- 整行可信度 = 元素置信度的最小值（不是平均 ✗ —— 一行有一个不确定就是不确定 ✓）；
- **输出三态**：`可直接用` / `建议复核` / `需人工`（按最坏元素定 ✓）。

## 五、数据与评测（本项目最大的"免费午餐"）

### 5.1 合成数据 = 反渲染（零人工标注）
```
samples/*.jps (+ 用户授权谱面)
   → layoutScore + renderScoreToSvg  ⇒ 干净基准图（已知真值 = 原 .jps ✓）
   → 图像增广：旋转 ±3°、透视、高斯噪声、运动模糊、JPEG 压缩、光照不均、
              纸张纹理、扫描线、局部遮挡、不同字体（引擎已有 SCORE_FONT_OPTIONS ✓）
   → 得到 (图, 真值 .jps) 对 ⇒ 训练/评测
```
- **优点**：真值绝对准确 ✓、可无限扩增 ✓、增广强度可调（可控难度曲线 ✓）；
- **局限**：合成分布 ≠ 真实拍照分布（**必须**留一批真实图片做"域外测试" ✓ —— 建议 P2 起收集 30–50 张真实谱面 ✓）。

### 5.2 评测指标（三层，缺一不可）
| 层 | 指标 | 目标（P2 验收） |
|---|---|---|
| 符号 | 检测/分类 **F1** | ≥ 0.95（干净合成）／≥ 0.80（真实拍照） |
| 文本 | `.jps` **编辑距离**（归一化） | ≤ 0.05（干净）／≤ 0.15（真实） |
| 版式 | 叠图 **IoU 均值** | ≥ 0.90 |
| 端到端 | **人工确认所需改动数**（每 100 小节） | ≤ 5 处（这是真正的产品指标 ✓） |

### 5.3 数据/隐私约定
- 用户图片**默认不外传**（选 C 路线时必须**显式告知并逐次确认** ✓）；
- 若走 B 路线，训练数据只使用**用户明确授权**的谱面 + 合成数据 ✓；
- 记录"哪些图走了外网"（诊断里可查 ✓，与既有诊断口径一致 ✓）。

## 六、落点与接口（与现有代码的关系）

```
packages/ijipu-omr/            ← 新增（纯 TS：类型、JSON↔.jps 生成器、自检闭环、置信度策略）
  ├─ src/types.ts              识别结果模型（含 bbox/conf）
  ├─ src/toJps.ts              JSON → .jps（**唯一语法出口**，只允许合法 token）
  ├─ src/selfcheck.ts          引擎自检 + 回修提示构造（纯函数，可单测 ✓）
  └─ src/evaluate.ts           F1 / 编辑距离 / IoU（评测与 CI 复用 ✓）
src/omr/                       ← 新增（应用 UI：复核界面 ⑦；走已有渲染与 cursorMap ✓）
src-tauri 或 src/omr/engine    ← 路线 A/B 的本地推理适配（Rust sidecar / ONNX；**新增依赖须先询问** ✓）
obsidian-ijipu                 ← 插件侧：命令「从图片生成谱面」（手机端拍照 → 走 C 或 B ✓）
CLI                            ← `ijipu omr -i 图片 -o 谱.jps [--json]`（复用 A·P1 的 CLI 骨架 ✓）
```

**与 CLI/插件方案的衔接（已有基建 ✓）**：
- CLI 的退出码语义可直接复用：识别成功 `0` / 有"待确认" `3` / 图片不可读 `2` / 自检不过 `4` ✓；
- 插件侧与"公开 API（B1）"同构：`api.omr(imagePath | dataUrl) → { jps, issues, confidence }` ✓
  （低置信 `issues` 就是"待确认清单" ✓，插件里可以直接给一个"确认面板" ✓）。

## 七、分阶段路线（每阶段都有可验收产物）

| 阶段 | 内容 | 验收 | 预估 |
|---|---|---|---|
| **P0 可行性**（1 周内） | 反渲染造 50 组合成图；用 C 路线跑通"图 → JSON → `.jps` → 自检 → 叠图"；出**误差画像**（哪类符号最爱错） | 干净合成图上编辑距离 ≤ 0.10；报告"哪些符号不可靠" | 3–5 天 |
| **P1 最小可用**（2 周） | 单声部 + 歌词 + 调号拍号；复核界面（点选联动 + 待确认清单） | 端到端"每 100 小节改动 ≤ 20 处"；CLI `ijipu omr` 可用 | 1–2 周 |
| **P2 加固** | 增广训练（B 路线起步）+ 真实图片评测集（30–50 张）；自检回修 2 轮 | F1 ≥ 0.8（真实）；每 100 小节改动 ≤ 5 处 | 3–4 周 |
| **P3 结构化扩展** | 多声部、临时段 `{bz}/{dsb}/{tp}`、装饰音（`&dy` 等）、力度记号 | 各结构单独评测；不支持的结构**明确标注待确认**（不瞎猜 ✓） | 4–6 周 |
| **P4 产品化** | 手机端拍照直转（B 路线离线模型）、批量导入、与插件/CLI 打通、文档与诊断 | 手机端可离线识别干净谱面；三处入口一致 | 视 P2/P3 结果 |

> **顺序原则**：每阶段**先补评测与断言**（§5.2 指标进 CI ✓），再谈准确率提升 —— 否则"感觉变准了"无法复现 ✗。

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **VLM 幻觉**（编出不存在的音符） | 致命（用户信任崩） | §4.2 三重自检（语法/小节时值/渲染）+ 强制 bbox + **不猜**进待确认 ✓ |
| 标注/训练成本高（B 路线） | 拖慢进度 | 先用**反渲染合成数据**起步；真实数据只做评测集（30–50 张）✓ |
| 真实拍照域差异大（阴影/透视/手写） | 准确率骤降 | P0 就做**误差画像**；增广覆盖；界面允许"整行重识别" ✓ |
| 中文歌词 OCR 错字 | 歌词错但音符对 | 歌词**允许后期批量替换**（按字个数对齐提示 ✓）；歌词正确率单独统计 ✓ |
| 外网/隐私（C 路线） | 用户不接受 | 逐次确认 + 诊断留痕；B 路线作为离线选项 ✓ |
| 新增依赖/模型体积（B 路线） | 违反"新增依赖须先询问" | **先问你**；优先 ONNX + 按需下载模型（不进安装包 ✓） |
| 期望管理 | "一键完美"落差 | 产品口径写清：**输出三态 + 待确认清单**，目标指标是"改动数"而不是"零错" ✓ |
